## Create and deploy a stack

1. **Stacks → Create stack**: pick the host (only when you have more than
   one), paste your `compose.yaml` (and a `.env` if you use one) and check
   the validation result.
2. Press **Create and deploy**. To only save the files and deploy later,
   turn off **Deploy after creating** first.

To start from a ready-made project instead, use **Create stack ▾ →
Create stack from template** (see [Templates](/docs/templates)).

Your files are the source of truth: Docker Manager deploys exactly what is
in them. Put files your services need, such as `./html` or a config file,
into the stack's **Files** tab before deploying.

Saving `compose.yaml` in the **Files** tab does not deploy it. Docker
Manager checks the file and shows the result above it, and the "Saved"
message has a **Deploy** button. Until you deploy, the stack shows
**Undeployed changes**, and its **Revisions** tab shows what changed with
**Deploy these changes** and **Restore deployed revision**.

### Deploy, update and clean up

- **Deploy** applies your files right away. It recreates only the services
  whose settings changed. If everything already runs as your files say, you
  see "Nothing to deploy" and **Last deploy** keeps its time.
- **Update** lists the services with a newer image, then downloads those
  images and recreates the services that use them. A dot on the button
  means newer images are available. To update on a schedule, use the
  stack's update policy (**Policies** tab).
- **Deploy ▾ → Pull images only** downloads newer images and changes
  nothing else. Press **Deploy** when you want to run them.
- **Start** and **Restart** run right away. **Stop**, **Take down** and
  **Delete** ask first and say what they do.
- When you remove a service from `compose.yaml`, its container stays on the
  host after a normal deploy. The stack page tells you so. To remove such
  leftover containers, press **Remove old containers** there, or open the
  menu next to **Deploy** and choose **Deploy and remove orphaned
  containers**.

In a stack's **Logs** tab, **Errors only** shows what the services wrote as
errors, and **Matching lines only** hides the lines without your search.
**Logs of** a service in its row menu opens the logs of just that service.

## Import projects you already run

**Stacks → Import project** lists the Compose projects running on a host
that Docker Manager does not manage yet. Press **Import** on one:

- If its folder is already in a place Docker Manager manages, it is adopted
  as it is. Nothing restarts.
- Otherwise Docker Manager moves it: it stops the project, copies its whole
  folder (the Compose file and every folder next to it, such as database
  data, with owners and permissions kept), checks the copy, and starts the
  project again from the copy. Its name and volumes stay the same. You are
  asked first when this stops running services; press **Stop and import**
  to go ahead.
- Docker Manager's own project is copied while it keeps running: nothing
  stops. Docker Manager moves onto the copy the next time you deploy that
  stack.

Projects Docker Manager already manages are hidden. Turn off **Hide managed
stacks** to see them.

To import projects that live elsewhere on the host, the agent needs to read
their folder. Add a read-only mount below `/import` to the agent in your
`compose.yaml` and run `docker compose up -d`:

```yaml
    volumes:
      # ...the existing lines...
      - /opt/stacks:/import:ro
```

Projects deployed by a tool that runs Compose inside its own container
(such as Arcane or Dockge) are found too: mount the folder where that tool
keeps its projects, for example
`/var/lib/docker/volumes/arcane_data/_data/projects:/import:ro`.

Good to know:

- If anything fails before the containers are recreated, nothing changes:
  the copy is removed and the project keeps running from its original
  folder.
- An import is refused, with the reason, when the running containers use
  settings that are not in the project's files. Most often the files were
  edited in the other tool but the project was not redeployed: redeploy it
  there first, then import again. If the other tool keeps variables in its
  own database, put them into the project's `.env` and try again.
- In the project's files, write full paths instead of `~` (for example
  `/root/.config/rclone`, not `~/.config/rclone`): `~` means a different
  folder for each tool.
- Your original folder is never changed. Delete it yourself once the stack
  runs well, and stop the old tool from managing that project so it does not
  redeploy or remove it.
- Remove the `/import` mount when you are done importing.

## Move a stack to another host

With more than one host, open the stack and choose **More stack actions →
Migrate**:

1. **Destination**: pick the host and press **Check destination**.
2. **Check**: Docker Manager lists what must be fixed first and what will
   be copied. Untick **Copy data** for a volume that should start empty, or
   tick **Copy image** to copy an image instead of downloading it. Changes
   are checked again before you can continue.
3. **Confirm** and **Move**: the stack stops, its folder and volumes are
   copied, and it starts on the new host. The old copy stays stopped until
   you remove it or start it again.

## Rename a stack

A stack's name is its Compose project name. It names its containers,
volumes and folder. To change it, open the stack and choose **More stack
actions → Rename**. Type the new name, for example `photos`, and press
**Preview changes** to see what will happen:

1. The stack stops.
2. Its volumes and its folder move to the new name. The data comes along.
3. Containers outside the stack that use those volumes are stopped and
   recreated with the new volume names. Those that were running start again.
4. The stack starts again under the new name.

Good to know:

- If the stack's `compose.yaml` sets `name:` at the top, change `name:` in
  the file first, then choose **Rename**: the new name is filled in for you.
  **Deploy** refuses until you do, so the stack never starts a second time
  with empty volumes.
- Containers outside the stack are only recreated if you are allowed to
  stop and remove them.
- If anything fails before the old containers are removed, everything goes
  back to how it was. If it fails later, the stack already has its new name:
  press **Deploy** to finish.
- Only the project name changes. To change the name shown in lists, use
  **Edit details**.

## Containers, images, volumes and networks

- To act on several at once, tick their rows. A bar above the list offers
  what you can do with them: **Start**, **Stop**, **Restart** or **Remove**
  for containers, **Remove** for images, volumes and networks. Before
  anything runs, you see the list of what it runs on.
- Some items are left out, with the reason: anything Docker Manager itself
  uses, Docker's predefined networks, containers that belong to a stack
  (remove them through the stack) and anything still in use. Removing
  several at once asks you to type a confirmation first.
- **Remove** is always the last entry of the **⋯** menu on an item's page.
- Images without a tag (older versions whose tag moved to a newer image)
  are folded at the end of the images list. Unused ones are safe to remove.

## Private images and builds

- **Registries** holds the logins Docker Manager uses to pull private
  images. **Test an image** shows which login an image would use.
- **Builds → Build image** builds an image from a Git repository. On a
  finished build, **Build again** repeats it and **Save as definition**
  keeps it for later. Build argument values are never stored: when you
  build again from the form, enter them once more.

## Invite people

**Access → Users → Invite user** creates a single-use link; send it
yourself. New people see nothing until you grant them access under
**Access → Groups** (to everything, one host, one stack and so on).

On a group's page, **Add members** moves people into the group. To set
its permissions quickly, pick a starting point under **Start from**:

- **Viewer** sees everything but changes nothing.
- **Operator** can also start, stop, restart and deploy, and read logs.
  It can't delete anything.
- **Admin** can do everything, risky actions included.

Adjust single actions afterwards if you need to. Nothing changes until you
press **Save permissions** and confirm the list of changes.

## Automatic updates, cleanup and backups

Nothing automatic or destructive runs until you turn it on:

- **Image updates** check whether the image behind a tag changed and
  recreate only the services that use it. There is no automatic rollback.
  The icon next to an image in the container and service lists shows its
  update state; select it to check that image again. On **Updates**,
  **Preview update** next to a stack or container shows the newer images,
  and when they were published if the registry says so, before you apply
  them.
- **Prune** removes unused containers, images, networks and build cache.
  Volumes need their own opt-in, and **Preview** shows what a run would
  remove.
- A policy's page says what it covers, when it runs next and how its
  recent runs went. **Schedules** lists every schedule in one place;
  **Change defaults** there sets what new policies start with.
- **Backups** use restic to local folders or S3-compatible storage. Your
  **Recovery Key** is shown once: store it outside Docker Manager. Without
  it, backups cannot be restored. A stack backup holds the stack's folder
  and its named volumes. Host folders it mounts from elsewhere, such as
  `/mnt:/mnt`, are left out unless you add them to the backup policy (and
  the host's agent allows them). **Manager state** is Docker Manager's own
  data: settings, users, stacks and your templates, drafts included.
  Include it in at least one backup policy that stores its backups away
  from the manager's own disk (S3, or a folder on another host).

### Set up backups

1. In **Backups**, press **Add backup repository**: a local folder or an
   S3 bucket. **Save and continue** saves it; then store the Recovery
   Key and type it once to confirm it. A local folder must be allowed on
   its host first (see [Configuration](./configuration#backups-to-a-local-folder)).
2. **Create backup policy**: what to back up (everything, minus what you
   untick), when, and how long to keep backups. **7 daily, 4 weekly, 12
   monthly** is a good start; **Custom** lets you set each rule. New
   policies start with their schedule off.

The **Overview** lists your policies with their last and next run; the
**Backups** tab lists every backup by run. A stack's or volume's
**Backups** tab says which policy covers it and when it runs next.

## Restore from a backup

Open a backup (from **Backups**, or the stack's or volume's **Backups**
tab), browse it and press **Restore**. You can restore a whole stack (its
files; deploy it again afterwards), some or all of its volumes (containers
using them stop and start again) or a single file. If a restore fails,
the original stays as it was.

If you lost the manager itself:

1. Install Docker Manager again as in the [Quickstart](./quickstart), with
   an empty data volume.
2. On the setup page choose **Import from backup**, enter where the
   backups are and your Recovery Key, pick a backup and import it.
3. Sign in with your old owner account. Users, stacks and settings are
   back. Create new API tokens, and connect every host again: create an
   install command under **Environments → Add environment** and run it on
   the host.

## Upgrade Docker Manager

Upgrade the manager first, then the agents. On the first host:

```bash
cd deploy/caddy
docker compose pull docker-manager && docker compose up -d docker-manager
docker compose pull docker-agent && docker compose up -d docker-agent
```

On every other host:

```bash
docker compose pull docker-agent && docker compose up -d docker-agent
```

After an upgrade, the web app shows **Reload to update**; reload when it
suits you.

### Go back after a failed upgrade

Before changing its database, the manager saves a copy of it. To go back,
restore that copy and run the image you had before:

```bash
docker compose stop docker-manager
docker compose run --rm --no-deps docker-manager snapshots list
docker compose run --rm --no-deps docker-manager snapshots restore <snapshot file>
```

Then set `image:` of `docker-manager` in `compose.yaml` to the previous
image (`code.neureka.dev/docker-manager/docker-manager@sha256:<digest>`) and
run `docker compose up -d docker-manager`. Anything done after the upgrade
is lost.
